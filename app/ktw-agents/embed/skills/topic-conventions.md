# Topic Conventions

This skill helps you choose the right topic family for an agent-coordination
problem and write the YAML + agent prompts that wire it up correctly.

Use this skill when:
- You're designing a multi-agent task where agents need to talk to each other
  beyond a simple parent → child handoff
- You see "coordinated team", "magentic", "shared state", "request approval"
  in the requirements
- An existing task uses topics and you need to read or extend it

## The five topic families

| Family | Purpose | Example topic |
|--------|---------|---------------|
| `child.<name>.*` | Spawner → workflow lifecycle (started/done/failed) | `child.researcher.done` |
| `to.<name>.*` | Direct agent-to-agent (message/task/result/cancel) | `to.alice.message` |
| `group.<team>.*` | Team broadcast (message/announcement) | `group.ingest.message` |
| `workflow.<id>.*` | Workflow lifecycle (started/done/failed) | `workflow.run-abc.done` |
| `protocol.<id>.*` | Structured request/response with correlation ID | `protocol.plan-1.plan-approval` |
| `ledger.<id>.*` | Shared mutable state (Magentic pattern) | `ledger.shared-plan.snapshot` |

Always **use the constructor functions** in
`internal/extensions/task/api/engine/topics.go` rather than writing topic
strings inline. Inline strings cause subtle typos that no compiler catches.

## Decide which topic family to use

```
Is this an event tied to a child machine's lifecycle (started/done/failed)?
  → child.<name>.* (always emitted by the spawner; subscribe in workflow YAML)

Is this an agent talking to ONE specific agent by name?
  → to.<name>.message
     (sender uses the send-message tool; recipient subscribes via mailbox bridge)

Is this an agent broadcasting to ALL members of a named team?
  → group.<team>.message
     (broadcast variant of the above; recipient subscribes via mailbox bridge)

Is this a request that needs a matched response (approval, permission, shutdown)?
  → protocol.<id>.<protocol-name>
     (correlation ID generated by sender; response uses the same ID)

Is this shared state that multiple agents need to read AND mutate?
  → ledger.<id>.{snapshot, update, complete}
     (use the ledger machine kind; agents use ledger-update / ledger-snapshot tools)

Is this a workflow's own start/end signal for external observers?
  → workflow.<runID>.* (auto-emitted by the workflow machine)
```

Detailed pattern catalog: get the instructions of skill `ktw-agents:/skill/topic-patterns`.

## Architecture notes

- **Topics are strings**. The bus is a `MemoryEventBus` (in-process for now,
  pluggable later). No wildcards — subscribers must subscribe to exact topic
  strings. Use the constructor functions.
- **Payloads are typed structs** that implement `EventStamper` so the
  executor auto-stamps `Type/Timestamp/Emitter` before publishing.
- **Mailbox ↔ EventBus bridge**: the orchestration plugin's
  `MailboxManager.SendMessage` mirrors sends to the appropriate `to.*` or
  `group.*` topic when an EventBus is attached via `SetEventBus`. This means
  `send-message` AND `to.<name>.message` subscriptions both see the same
  message — pick whichever surface fits your subscriber.
- **Ledger machine**: an event-driven machine (no LLM cost) that holds a
  shared JSON document. Agents emit RFC 7396 merge patches via
  `ledger-update`; subscribers receive snapshots via `ledger-snapshot`. See
  the Magentic example sub-skill.

Full namespace + payload field list: load skill `topic-namespace`.

## Worked example 1 — Coordinated team

Manager agent dispatches work to specialists via direct topics, collects
results, and synthesizes. Load skill `topic-coordinated-team` for the full
walkthrough.

Key shape:

```yaml
type: agent
config:
  mode: coordinator
  plugins: [standard]
---
You are the coordinator. Use `delegate(mode: background, task_name: ..., prompt: ...)`
to spawn specialists. Use `check-messages` to read replies on `to.coordinator.message`.
Synthesize once all specialists have replied, then call `complete`.
```

Specialists call `send-message(to: "coordinator", message: ...)` to send
results back. The mailbox bridge ensures the message lands in coordinator's
mailbox.

## Worked example 2 — Magentic (shared ledger)

Manager + specialists coordinate via a shared `ledger` machine that holds the
plan and assignment state. Agents read with `ledger-snapshot`, mutate with
`ledger-update`. Load skill `topic-magentic` for the full walkthrough.

Key shape:

```yaml
type: workflow
config:
  steps:
    - kind: parallel
      branches:
        - name: shared-state
          task: { type: ledger, id: "magentic-demo", initial: { plan: {...} } }
        - name: manager
          task:
            type: task
            plugins: [standard, ledger]
            prompt: |
              Read snapshot, assign tasks via ledger-update, poll until results in
        - name: alice
          task:
            type: task
            plugins: [standard, ledger]
            prompt: |
              Watch ledger-snapshot for your assignment, do work, post result
```

## Common pitfalls

1. **Forgetting to add the plugin** — `ledger` plugin is opt-in (`plugins:
   [standard, ledger]`). Without it, agents have no `ledger-update` /
   `ledger-snapshot` tools.
2. **Building topic strings by hand** — use `engine.AgentMessageTopic(name)`
   etc. from `topics.go`. Inline strings cause silent miss-routing.
3. **Direct vs group confusion** — `to.alice.message` reaches alice ONLY
   even if alice is in a team. `group.color-team.message` reaches every
   teammate of color-team. Pick consciously.
4. **Ledger ID mismatch** — workflow children use a literal `id:` in the
   ledger config so siblings can share it. The ledger machine's auto-assigned
   runID is NOT what other agents address. Always set `id:` explicitly.
5. **Coordinator without a mailbox** — `mode: coordinator` agents don't
   automatically subscribe to a topic. They poll their mailbox via
   `check-messages` (which the orchestration plugin populates from the
   bridge).
