# PRD

Reference for generating a structured Product Requirements Document.

---

## Purpose

Generate a Product Requirements Document (PRD) from a product idea, prompt, or description. Covers overview, objectives, target audience, features, user stories, functional and non-functional requirements, success metrics, and timeline.

## Scope

Input: a product idea, concept description, feature prompt, or application outline.

## Process

### Step 1 -- Analyze the product concept

Read the input fully. Identify the product concept, functionality, and target users. Clarify ambiguities by making reasonable assumptions (document them in the PRD).

### Step 2 -- Produce the PRD

Output in Markdown. Use bullet points, subheadings, and tables where appropriate. Use formal, precise language suited for business and technical audiences. Ensure each requirement is specific, testable, and unambiguous.

The document must contain these sections in order:

### Overview

Summarize the product concept, its purpose, and the problem it solves.

### Objectives

List the primary goals and business value of the product.

### Target Audience

Define the intended users, their needs, and their characteristics.

### Features

Break down the product into features. Highlight MVP features and priorities where relevant.

### User Stories

Write user stories for the key features in standard format:

As a [role], I want to [action] so that [benefit].

### Functional Requirements

List specific, testable functional requirements organized by feature or module.

### Non-functional Requirements

Cover performance, security, scalability, accessibility, and other quality attributes.

### Success Metrics

Define measurable criteria for evaluating the product's success.

### Timeline

Provide a phased timeline with milestones. Use placeholders if actual dates are not provided.

## Output Format

Markdown document using bullet points, subheadings, and tables where appropriate. Sections in order: Overview, Objectives, Target Audience, Features, User Stories, Functional Requirements, Non-functional Requirements, Success Metrics, Timeline. Formal, precise language suited for business and technical audiences.

## Constraints

- Include mock data or placeholders if actual data is not provided in the input.
- Every requirement must be specific, testable, and unambiguous.
- User stories must follow the format: As a [role], I want to [action] so that [benefit].
- Use formal, precise language suited for business and technical audiences.
